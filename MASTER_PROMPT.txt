1. CORE DEVELOPMENT PRINCIPLES

Observe the following mandatory principles throughout development.

1.1 Reuse established technologies

Do not reinvent functionality that is already provided by mature, maintained and security-reviewed libraries.

Before implementing any major feature:

1. Search for established Django packages and maintained libraries.
2. Inspect their documentation, compatibility, maintenance status and security history.
3. Prefer official integrations and established open-source projects.
4. Evaluate dependencies for known vulnerabilities.
5. Use existing libraries where they adequately meet the requirements.
6. Write custom application code only for business-specific functionality.

Do not introduce unnecessary dependencies.

Avoid abandoned packages, unmaintained repositories, unknown binaries and libraries with unresolved critical vulnerabilities.

Maintain a dependency inventory and document why major dependencies were selected.

1.2 Security-first engineering

Security must be considered at every stage, not added after development.

Apply secure development principles including:

- Secure by default.
- Least privilege.
- Defence in depth.
- Zero trust between application components.
- Data minimisation.
- Separation of duties.
- Secure session management.
- Explicit authorisation.
- Fail-safe error handling.
- Comprehensive auditability.

Follow OWASP ASVS Level 2 as the principal application security verification target, with additional controls for sensitive financial and personal data.

Use OWASP Top 10 guidance, OWASP API Security Top 10 and relevant secure coding standards.

1.3 Modular monolithic architecture

Develop the application as a modular Django monolith.

Keep business domains separated into Django applications while maintaining a shared authentication and database foundation.

Do not introduce microservices unnecessarily.

The system must be capable of future API integration with other Northern Highways Transporters applications without requiring architectural reconstruction.

1.4 Complete functionality

Every major interface must connect to working backend functionality.

Do not use hardcoded statistics, simulated payment confirmations, fabricated member records or static demonstration data in production functionality.

Development fixtures and sample data must be clearly separated from production records.

9. SECURITY REQUIREMENTS — CRITICAL

Security is a mandatory architectural requirement.

The application will process personal identification details, contact information, financial records, vehicle ownership information and regulatory documents.

Treat this information as sensitive.

9.1 Authentication

Use Django's established authentication system.

Requirements:

- Secure password hashing.
- Strong password policy.
- Login rate limiting.
- Account lockout or progressive throttling.
- Secure password reset.
- Session expiry.
- Session invalidation after password changes.
- Optional MFA.
- Secure cookies.
- Protection against session fixation.

Never store passwords in plaintext.

Never log passwords, authentication tokens or session cookies.

9.2 Authorisation

Implement granular RBAC and object-level permissions.

Check authorisation on the backend for every sensitive request.

Do not rely on hiding frontend buttons.

Prevent insecure direct object references.

Test that members cannot access another member's:

- Personal information.
- Vehicles.
- Documents.
- Invoices.
- Payments.
- Statements.
- Complaints.

Require additional permissions for financial adjustments, approvals, exports and administrative actions.

9.3 Data encryption

Use HTTPS/TLS for all production connections.

Encrypt sensitive stored information where appropriate.

Protect:

- National identification numbers.
- Sensitive personal information.
- Integration credentials.
- Private documents.
- Backup archives.

Use managed secrets or environment-based secret injection.

Do not commit ".env" files.

Do not expose secret values in generated source code.

Consider field-level encryption for especially sensitive identity information, with secure key management and a documented rotation strategy.

9.4 Application security

Protect against:

- SQL injection.
- Cross-site scripting.
- Cross-site request forgery.
- Broken access control.
- Insecure direct object references.
- Server-side request forgery.
- File upload attacks.
- Path traversal.
- Session hijacking.
- Clickjacking.
- Brute-force attacks.
- Mass assignment.
- Unsafe deserialisation.
- API abuse.
- Sensitive data exposure.

Use Django ORM safely.

Validate uploaded files by actual content, not filename extension alone.

Set upload size limits.

Reject executable files.

Use private storage.

Apply appropriate security headers and Content Security Policy.

9.5 Audit logging

Maintain comprehensive audit trails for:

- Login attempts.
- User creation.
- Role changes.
- Member record changes.
- Vehicle ownership changes.
- Document uploads.
- Document approvals.
- Invoice creation.
- Invoice adjustments.
- Payment recording.
- Payment reversals.
- Expense approvals.
- Data exports.
- Administrative configuration changes.

Each audit entry should capture:

- Actor.
- Action.
- Entity.
- Timestamp.
- Relevant record identifier.
- Outcome.
- Appropriate change metadata.

Avoid recording secrets or unnecessary personal information in logs.

Audit records should be protected from modification by ordinary administrators.

9.6 Privacy and data protection

Implement controls consistent with Kenya's Data Protection Act, 2019 and applicable regulations.

Provide:

- Privacy notices.
- Purpose limitation.
- Data minimisation.
- Configurable retention policies.
- Secure deletion workflows.
- Member data access procedures.
- Data correction procedures.
- Access logging.

Implement:
